# AirPodsTracker：只用 iPhone 的可行性核查与改进建议

调研日期：2026-10-11。目标：只用 iPhone，尽量自动记录 AirPods 使用情况，并让充电与续航记录更省事、可信。

本次阅读了《完整开发方案》和《UI交互与视觉交付方案》，检索了 GitHub、Apple 官方文档、开发者论坛及相关产品资料，并抽查部分源码。下文是调研结论与开发建议，不是已完成的 App，也不代表已通过用户 iPhone 真机验证。文档中的实现 Prompt 仅作为被审阅资料。

## 1. 结论

原方案值得继续做，但要重做采集路径与统计定义。

- **最值得实现**：蓝牙连接/断开个人自动化调用 App Intents，保存起止事件；不要求追踪 App 全天运行。
- **可增强**：支持的耳机通过 Core Motion 提供摘戴相关信号；可选聆听健康功能通过 HealthKit 事后导入有记录的音频暴露区间。
- **最值得先实测的电量线索**：AllMyBatteries 与快捷指令的桥接。已有作者发布基于该 App 的 AirPods 电量阈值自动化，但尚未核清左右耳、盒子、更新时间的输出结构。
- **可以独立实现的兜底**：用户分享电量截图，本地 OCR 识别并确认；锁屏/桌面入口快速记录充电；异常记录校正；可比较的个人续航趋势。
- **目前不能承诺**：一个普通独立 iOS App 在所有状态下，完全自动、全天、无漏记地获得每次摘戴及左右耳/盒子实时电量；也不能用时长推算真实电池健康百分比。

“连接时长”“佩戴时长”“系统记录的聆听时长”“耗电量”应分别存储与展示，不能互相替代。

## 2. 原方案需要直接修正的问题

| 原方案做法 | 问题 | 建议 |
|---|---|---|
| 音频路由变化 = 戴上/摘下 | 路由表示音频输入输出，既不是全局蓝牙日志，也不是播放或佩戴证明 | 蓝牙自动化作为连接事件来源；摘戴与聆听另取证据 |
| 断开时仍遍历 currentRoute 找 AirPods | 耳机离开后，当前输出通常已变为扬声器，可能永远收不到结束记录 | 检查通知中的 previousRoute，并比较新旧输出 |
| 后台保存时间戳，回来补算 | 能算时间差，不能恢复未知断开时刻 | 没有结束证据的时段标为待确认，不一直计到下次打开 |
| 启动就激活 playAndRecord | 这是录放音配置，默认不可混音，可能打断其他音频；蓝牙 HFP 选项也不是全局监听许可 | 追踪功能不为监听而占用录放音会话 |
| 设备名包含 AirPods 即识别 | 用户可以改名；同名设备可能冲突 | 自动化首次明确选择设备，App 内建立设备槽位；路由名称仅作辅助 |
| 官方总续航 − 已用时间 = 剩余电量 | 忽略音量、通话、降噪、单耳、待机、补电和缺测 | 仅作明确标识的估算；有个人可比数据后再给范围 |
| 盒子满到盒子空 = 完整续航 | 起点耳机未必满，盒子空时耳机可能仍有电 | 定义“充电观察区间”；完整样本需要明确耳机与盒子起止条件 |
| 实测/官方 = 电池健康 | 使用条件不同就会改变结果，无法据此识别容量老化 | 改为“相似条件下的个人续航变化” |
| 删除充电周期级联删除使用记录 | 误删充电标记会丢失独立的使用历史 | 删除关联或重新归属，保留使用记录 |
| AppIntents 自动取得耳机电量 | AppIntents 暴露应用自己的动作，不自动授予附件电量能力 | 电量数据源单独验证 |

路由行为与 previousRoute 用法见 [Apple 音频路由处理](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes)；挂起机制见 [Apple DTS 后台执行说明](https://developer.apple.com/forums/thread/685525)；音频配置见 [playAndRecord](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playandrecord) 与 [allowBluetoothA2DP](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/allowbluetootha2dp)。

## 3. 可以比原方案做得更好的自动记录

### 3.1 主路径：蓝牙自动化 → App Intent → 事件记录

用户首次在快捷指令中为指定耳机设置连接、断开两条个人自动化，选择“立即运行”。每条只调用一个动作，快速写入事件，不打开主界面，也不持续运行计时器。

Apple 正式说明确认 iOS 17 起蓝牙自动化可立即运行；断开触发在设备厂商公开的 iOS 17 操作截图中也有展示。Apple 在线触发器指南目前仍只描述连接，不能把这一文档遗漏当成断开触发不存在。[Apple 更新说明](https://support.apple.com/111098)、[厂商原始操作手册](https://www.manual-en.m-gears.com/autohotspot-iphone)

App Intent 可以配置锁屏可执行，但动作真正落库仍受执行环境和文件保护影响。目标是系统事件驱动，不能承诺每次均无延迟。保存的 Date 是动作执行时间，不冒充硬件事件精确时刻。[Apple authenticationPolicy](https://developer.apple.com/documentation/appintents/appintent/authenticationpolicy)

设计上只需保存：事件 ID、设备槽位、事件类型、执行时间、来源。重复开始不新建第二个会话；孤立结束不编造开始；短时重连可以合并展示，同时保留原始边界。App 重开时依据事件重建统计，跨午夜按日拆分。

**限制**：初次设置需要用户在系统里操作；蓝牙仍连接但摘下单耳或暂停播放时，不保证出现断开事件。自动化只能首先证明“连接区间”。

### 3.2 摘戴辅助：Core Motion 是原方案漏掉的官方能力

Apple WWDC23 明确：支持头部追踪的耳机，在开启自动入耳检测时，摘下与戴回会触发 CMHeadphoneMotionManager 的断开/连接相关事件。运动数据来自一只耳机，系统可在左右耳之间切换。因此，数据流来自左耳不等于只有左耳佩戴。[Apple WWDC23](https://developer.apple.com/videos/play/wwdc2023/10179/)

可以用它改善可观测时段的摘戴判断；运行前检查硬件支持和运动授权。**这不等于获得全天后台唤醒或摘戴历史**。前台成功不能证明挂起、锁屏、强退后也有效。

iOS 18 起另有 CMHeadphoneActivityManager，Apple 提供活动变化示例，可留作后续兼容性试验，无需为首版扩张功能。[Apple 耳机活动示例](https://developer.apple.com/documentation/coremotion/getting-motion-activity-data-from-headphones)

### 3.3 可选补录：HealthKit 的耳机音频暴露记录

headphoneAudioExposure 的数值是声音暴露水平，不是使用小时数。样本有起止时间，可以据此计算“系统记录到的耳机音频暴露区间”。这条路径适合解锁后补充历史，而非实时停表。[类型定义](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/headphoneaudioexposure?language=objc)、[HKSample](https://developer.apple.com/documentation/healthkit/hksample)

需要检查真实样本的耳机设备信息与写入来源；不能假设 device 总有值、标识总稳定。按 UUID 导入、处理删除、合并重叠区间，避免双重计时；如样本包含数量序列，要核实明细，不能把大区间直接当连续聆听。[HKObject](https://developer.apple.com/documentation/healthkit/hkobject)、[HKAnchoredObjectQuery](https://developer.apple.com/documentation/healthkit/hkanchoredobjectquery)

拒绝读权限可能表现为空数据，锁屏时数据库可能不可读；空数据不能推断“没有使用”。佩戴着只开降噪、不播放，也可能耗电却没有对应聆听暴露记录。[权限说明](https://developer.apple.com/documentation/healthkit/hkhealthstore/authorizationstatus(for:))、[锁屏访问错误](https://developer.apple.com/documentation/healthkit/hkerror/errordatabaseinaccessible)

这应是用户主动开启的真实聆听健康功能。Apple 要求 HealthKit 具有健康/健身用途，不能为了电池统计借用健康权限。[Apple 隐私与用途要求](https://developer.apple.com/documentation/healthkit/protecting-user-privacy)

## 4. 电量：不要轻率宣布不可能，也不要假装已破解

### 4.1 最有价值的候选：同一台 iPhone 上桥接 AllMyBatteries

从 App Store 的开发者网站链接核对到的官网宣称：耳机连接 iPhone 后，刷新可取得耳机和盒子电量，并支持 Siri/Shortcuts。App Store 列出 AirPods 监测、历史记录和快捷指令集成；它是免费下载、含内购，不能把所有功能称为免费。[开发者官网](https://allmybatteries.jylljy.com/)、[App Store](https://apps.apple.com/us/app/allmybatteries/id1621263412)

GitHub 上 jamesjingyi/ios-shortcuts 作者公开了依赖 AllMyBatteries 的 AirPods 低电量提醒，并说明放在断开自动化里使用。这说明已有作者描述过基于数值判断的用法，比纯猜测“可能支持”更有依据。[作者的 Batteries 示例](https://github.com/jamesjingyi/ios-shortcuts#-batteries)

**仍未证明**：当前版本动作是否返回数字；能否分别输出左耳、右耳、盒子；返回的是新采样还是缓存；是否有原始更新时间；是否锁屏可运行；这些动作是否受内购限制。本次未能解析公开 iCloud 快捷指令内容，也未在 iPhone 安装运行。

若测试通过，可以采用：蓝牙连接/断开 → 电量动作 → AirPodsTracker 的记录电量 Intent。这仍然只用 iPhone，但依赖一个第三方应用及其版本。如果它只能显示电量而无法导出，不把它硬接入首版。

开发者写的后台更新间隔只是产品描述，不能视为 iOS 固定调度承诺。即便可读取，也要显示“何时更新”，盒子闭合后旧数值不能继续标成实时电量。

### 4.2 为什么不直接照搬 Android/macOS 电量解析器

AirPods 使用厂商协议，缺少标准 BLE Battery Service 并不能单独证明完全不可读取；但拿到原始广播与解析广播是两件事。

研究项目 BTLEmap 记录了 iOS 对 Apple 厂商广播及部分 GATT 服务的过滤，其突破方案依赖特殊授权或越狱条件。它是平台边界证据，不是普通 iPhone App 的现成电量 SDK。[BTLEmap](https://github.com/seemoo-lab/BTLEmap)

当前 Core Bluetooth 文档确实增加 iOS 26 + Live Activity 的后台扫描能力；然而 Apple 工程师补充，锁屏且屏幕熄灭后会恢复扫描限制，没有受支持的绕过方式。因此不能把新文档理解成全天熄屏自由扫描，更不能推导出 Apple 厂商广播一定可见。[Core Bluetooth](https://developer.apple.com/documentation/corebluetooth)、[Apple 工程师说明](https://developer.apple.com/forums/thread/815189)

结论：自研公开 API 路线尚未找到足以承诺完整电量采集的可复用实现。普通侧载也不应被视为自动获得系统私有权限。

### 4.3 可独立实现的电量兜底：截图识别

用户把系统电池视图的截图分享给 App，使用 Vision 本地 OCR 提取百分比；结合布局判断对应设备，识别不清时让用户确认。没有显示出来的某只耳机或盒子必须保持未知，不能补成 0%。[Apple Vision 文字识别](https://developer.apple.com/documentation/vision/recognizetextrequest)

这比反复手输数字方便，但仍需要用户主动截图/分享；普通 App 不能据此静默读取其他 App 的屏幕。记录截图采集时间与导入时间，旧截图不作为实时值。

## 6. 最值得增加的功能

以下是产品建议，示例数字均为界面举例，不是实测结果。

| 优先级 | 功能 | 用户实际得到什么 | 约束 |
|---|---|---|---|
| P0 | 自动化安装自检 | 设置完取放一次耳机，直接显示“开始收到/结束收到”，避免用了几天才发现没记录 | 只能证明自检场景；锁屏与强退另测 |
| P0 | 自动补账与异常修正 | 日常静默；只在缺少结束、异常长记录时出现一张修正卡，可一键结束或改时间 | 缺失就是未知，不能虚构停止时刻 |
| P0 | 每个数字带来源与新鲜度 | “盒子 60% · 20 分钟前”，与“预计还能用约 2–3 小时”清楚区分 | 采样时间未知时就明说，不能拿导入时刻冒充 |
| P0 | 充电只记一次动作 | 锁屏/桌面/快捷指令入口记录“充满”或“中途补电”，操作后可撤销 | NFC 也只是快捷录入，不能证明实际已满 |
| P1 | 够不够下一段使用 | 用户输入“还要听 2 小时”，以近期有效电量和可比续航给建议 | 数据不足就显示无法判断，不输出虚构概率 |
| P1 | 部分补电也能记 | 不必等盒子耗尽；自然充电后结束观察区间，区分完整与提前结束 | 提前充电记录不能当完整续航样本拉低均值 |
| P1 | 个人续航趋势 | 比较相似条件下的记录，提示“近期记录变短”，并显示样本数 | 不诊断老化；单耳、通话、降噪等未知就不假设 |
| P2 | 桌面与锁屏一眼看懂 | 当前记录、今日确认时长、最近电量、一个主要操作 | Live Activity 是展示入口，不是后台永生机制 |

续航预测起步用可比记录的简单统计即可，无需大模型。没有有效电量锚点和足够样本时，漂亮的预测也没有依据。

## 7. UI 方案建议保留与调整

保留：清晰的大数字、原生系统材质、适量触觉、明暗主题、结束时的简短统计。

调整：

- 首页优先显示“记录是否正常、今天记录多少、最近电量何时更新、下一步能做什么”；历史和趋势降为次级页面。
- 没有真实电量时不画伪实时电池水位；估算用区间，未知用占位，不用绿色满环粉饰。
- 必要操作使用可见按钮；双指捏合、长按隐藏菜单和 0.8 秒蓄力不应成为必经路径。
- 删除仅按时长推断的“通话/专注/飞行”标签，以及模仿真实音频的随机声波。
- 删除“81% 说明老化”“92% 新机水准”等不成立的结论。
- 不用“连续四小时佩戴、凌晨持续使用”作为奖励；休息提醒由用户自定，不能把一个计时阈值称为听力风险测量。
- 连续粒子、陀螺仪水波、脉冲只作可关闭的少量装饰，并支持减少动态效果、较大文字和 VoiceOver。

## 8. 开发前最小验证顺序

这三个试验比先写四个完整页面更能降低返工。

1. **连接事件试验**：两个自动化写入起止时间。对照人工记录，测试正常取放、锁屏熄屏、App 挂起/强退、重启首次解锁前后、低电量、快速重连、仅摘一耳、切换扬声器。输出漏事件与延迟记录，不用模拟器结果代替真机。
2. **电量桥接试验**：检查 AllMyBatteries 当前快捷指令动作与输出，开盒/闭盒/连接/断开逐一与系统视图比对；核清三个部件、采样时刻、缓存和费用。失败则首版采用 OCR/手动快照，而不是转向无限期私有协议逆向。
3. **可选补录试验**：若用户需要聆听健康，读取真实 HealthKit 样本，检查来源、设备、延迟与重叠；若耳机支持，分别验证 Core Motion 摘戴信号在前后台的覆盖范围。

通过标准由实际事件覆盖率、时间误差、额外耗电和操作次数决定；本次没有真机数据，因此不给成功率或工期承诺。

首版建议范围：事件自动记录、异常修正、充电观察记录、有效电量快照、今日/近七天统计、一个快捷入口。电量桥接、Core Motion 和 HealthKit 按验证结果接入，不能让一个不确定能力拖住全部功能。
